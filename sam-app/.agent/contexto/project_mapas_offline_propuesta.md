Pedido del cliente (17-jul-2026, "quiero recuperar la confianza del cliente"): mapas tipo Avenza (como FieldMaps) dentro de ASM, **offline**, sin cargar el servidor de ASM ni afectar su rendimiento; GPS solo dentro del visor. + Auditoría de rendimiento con agentes. Documento completo: **`sam-app/docs/propuesta-mapas-offline-y-perf.md`**.

## Propuesta recomendada (Fase 1, 1-2 días) — PENDIENTE DE APROBACIÓN
Módulo "Mapa" **lazy** (`React.lazy`, chunk ~50 KB gzip, arranque +0) con **Leaflet** (42 KB gzip, NO maplibre 275 KB) usando los **tiles XYZ PNG ya generados por FieldMaps** (bucket público `tiles`, `https://api.mapview.surcoapp.tech/storage/v1/object/public/tiles/{org}/{map}/{z}/{x}/{y}.png`, cache 1 año; RIOPAILA = 1.118 tiles ≈ 40-50 MB, maxzoom 16 + overzoom 4). Offline tipo Avenza: botón **"Descargar mapa"** → tiles a Cache Storage con progreso + `storage.persist()` + gestor "Mis mapas". GPS `watchPosition` high-accuracy **solo con visor abierto** + wake lock opt-in. Config del mapa hardcodeada o `meta.json` en el bucket (la tabla `maps` de FieldMaps es RLS-only-members; los tiles sí públicos). Servidor ASM: 0 requests. FieldMaps: solo GETs estáticos. Fase 2 opcional: PMTiles (1 archivo/mapa → OPFS). Descartado: iframe (no offline, doble login) y portar maplibre (peso). Código portable de FieldMaps: `gps.ts` (círculo precisión), `orientation.ts` (brújula), `measure.ts` (turf).

## Auditoría de rendimiento ASM (3 agentes) — hallazgos top
Base SÓLIDA (Dexie fase-1 <50ms, delta sync, versionado maestro, xlsx lazy, precache por hash — NO romper). Consumo actual ~2-3 MB/día/operario. Hallazgos priorizados:
1. **Re-render global cada 30 s** (poll siempre devuelve array nuevo + context value sin memo → 20 consumidores). 2. **Listas sin tope + `maestro.find` 15K por ítem en render** (freeze 1-3 s al filtrar Completada). 3. **Buscador en App.tsx re-renderiza el God-file por tecla** (O(1000×15K) con filtro ingenio). 4. **Primer arranque bloquea Login hasta 10 fetches** (10-30 s rural). 5. Full sync ×2 con `select('*')` (~250 KB/apertura, −30-50 % posible). 6. **Landmine `PGRST_DB_MAX_ROWS`**: si vuelve a 1000, maestro se trunca silencioso (paginación asume limit=20000). 7. Invalidación maestro todo-o-nada (1 edición → 50 dispositivos × 2 MB pico 6 am). 8. Iconos gordos en precache (~250 KB gratis).
Quick wins en orden: 8 → 5 → 6 → 2+3 → 1 → 4 → 7.

## 🔴 Incidente pantalla blanca (17-jul) y regla resultante
Los deploys con `React.lazy` (chunks MapaView/MapasTab) tumbaron producción: **el build de VERCEL partió el bundle distinto al local** (chunk `jsx-runtime` de 330 KB que el build local no generaba) → crash de arranque → pantalla blanca. El build local pasaba, por eso no se detectó. **Revert inmediato (274bf6a) restauró el servicio.** Reintroducido en `0f4def0` con **imports ESTÁTICOS** (sin lazy): estructura de chunks idéntica a la histórica (index + xlsx), +49 KB gzip aceptados. Verificado con vite preview local + navegador y LUEGO producción con navegador (login renderiza, 0 errores consola).
**REGLAS:** (1) ⚠️ NO introducir `React.lazy`/chunks nuevos en esta app sin verificar el PREVIEW REAL de Vercel (rama `pruebas`) — el chunking de Vercel puede diferir del local; (2) tras todo deploy estructural, verificar producción con el navegador (get_page_text + consola) — el usuario atascado tras un deploy roto se arregla con incógnito/recargas dobles/borrar datos del sitio (el SW roto se auto-cura con el sw.js nuevo); (3) el caso "app no carga tras deploy" → revert primero, diagnóstico después.
